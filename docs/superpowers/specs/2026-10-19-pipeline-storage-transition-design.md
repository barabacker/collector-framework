Дата: 2026-10-19
Статус: согласована пользователем; реализована и проверена 2026-10-19.

## Цель и границы

Пользователь задаёт классы pipeline в Settings. Движок создаёт компоненты на
каждый обход и управляет их жизненным циклом. Компоненты приложения определяют
запись в файл или базу. Чтение, экспорт, схема хранения и объединение сущностей
также принадлежат приложению; collector не поставляет хранилища и читатели.

Переход реализуется отдельно от mark_incomplete, collector.testing, HTTP
status helpers и inprotect. Эти предложения не отменяются, но не входят в ветку.
Не менять trading_platform, его uv.lock и существующее изменение pyproject.toml.
Не запускать MongoDB, миграции, ETL, live-тесты или сбор данных.
Не добавлять зависимости pymongo, itemadapter, драйверы баз и обязательные схемы items.
Python остаётся >=3.11. Сетевые тесты остаются opt-in.

## Согласованные решения

- Settings.pipelines содержит классы в порядке обработки.
- Settings.pipeline_options содержит настройки компонентов.
- Для каждого Crawl создаются новые экземпляры, даже для одного crawler_cls.
- Создание через from_crawler(crawler), если метод есть; иначе cls().
- Методы: open_crawler(), process_item(item), close_crawler().
- process_item возвращает значение следующему компоненту; None допустим как item.
- Ошибка pipeline завершает свой обход независимо от max_errors.
- crawl_many сохраняет изоляцию обычных ошибок, статистику и Outcome.
- Запись принадлежит пользовательским pipeline. Встроенные SqlitePipeline,
  JsonLinesPipeline, MongoPipeline и DatasetPipeline не добавляются.
- collector.storage и dataset= удаляются как явно несовместимое изменение.
- ctx.sink остаётся каналом передачи прикладного ресурса для чтения краулером.

## Предлагаемые уточнения контракта для проверки

Settings получает поля с пустыми значениями по умолчанию:

```python
pipelines: Sequence[type] = ()
pipeline_options: Mapping[str, Any] = field(default_factory=dict)
```

Компоненты считаются обычными Python-объектами: наследование от общего базового
класса не требуется. Строковые пути импорта, приоритеты-числа, signals и глобальный
реестр не добавляются. from_crawler — синхронная фабрика; конструктор не открывает
внешние ресурсы. Async setup выполняется в open_crawler.

process_item обязателен; open_crawler и close_crawler необязательны. Эти три метода
могут быть синхронными или возвращать awaitable. Движок дожидается awaitable;
синхронные методы выполняются в event loop, без неявного переноса в поток.
Для блокирующей записи приложение использует асинхронный драйвер или свой executor.

Настройки рассматриваются как read-only. Изменяемое состояние хранится в экземпляре
pipeline, а не в Settings или атрибутах класса. Независимость экземпляров не означает
глубокого копирования произвольных объектов из pipeline_options.

## Сборка и время жизни

Общий механизм интегрируется в Crawl, а не отдельно в каждый runner: прямой Crawl,
open_crawl, crawl, run_crawler, collect и crawl_many получают одинаковое поведение.
Если open_crawl открыт, но run/stream не вызван, pipeline не открывает ресурсы.

Порядок запуска:
1. Начать измерение запуска и создать компоненты.
2. Последовательно открыть pipeline в порядке Settings.pipelines.
3. Вызвать crawler.opened().
4. Получить start_requests(), запустить работников.

Порядок закрытия:
1. Остановить и дождаться работников; никто больше не использует ресурсы.
2. Вызвать crawler.closed(stats), только если crawler.opened() успешно завершился.
3. Закрыть успешно открытые pipeline в обратном порядке; попытаться закрыть каждый,
   даже если другой close завершился ошибкой.
4. Завершить статистику запуска. HTTP закрывается внешним open_crawl.

Компонент без open_crawler считается открытым, когда до него дошёл этап открытия.
Компонент, чей open_crawler упал или был отменён, сам освобождает частично открытые
ресурсы. Закрытие уже открытых компонентов обеспечивает движок.

Ресурс, помещённый pipeline в ctx.sink, заимствуется краулером: движок автоматически
не вызывает sink.close(). Владение общим внешним ресурсом остаётся у приложения.
Компонент, устанавливающий sink, обязан отказать при уже занятом ctx.sink, а не
молча заменить ресурс; это правило прикладного компонента, не универсальная
интроспекция ресурсов со стороны collector.

## Обработка элементов

```text
callback -> crawler.process_item(item) -> pipelines по порядку -> stream/collect
```

Возвращаемое значение существующего crawler.process_item игнорируется, как прежде.
В stream и collect попадает результат последнего pipeline. При пустом pipelines
старое поведение сохраняется, кроме явно удаляемого Dataset API.

stats.items сохраняет существующее значение: число элементов, выданных callback,
а не число гарантированно сохранённых записей. DropItem и новые счётчики обработанных
или отброшенных элементов в этот этап не входят.

Порядок pipeline гарантируется для одного элемента. Разные работники могут
параллельно вызывать один экземпляр pipeline. Приложение отвечает за синхронизацию
своего ресурса; глобальный порядок элементов и exactly-once не обещаются.

## Ошибки и отмена

Ошибка создания, открытия, обработки или закрытия pipeline делает обход неуспешным.
Для таких ошибок предлагается stats.reason='pipeline_error'. Обычные ошибки HTTP,
парсера и существующего crawler.process_item продолжают следовать max_errors.
Не классифицировать произвольный ValueError как ошибку pipeline: важен этап вызова.

При первой ошибке обработки pipeline выставить фатальное состояние до следующего
ожидания. Прекратить приём новых работ и отменить/дождаться остальных работников.
Уже завершённые записи не откатываются; прерванная операция может иметь побочный
эффект. Повторов записи, транзакций и автоматического rollback не добавлять.
Ошибка обработки связывается с её Request в crawl.errors и увеличивает stats.errors;
ошибки setup/close не снабжаются вымышленным Request.

Через open_crawl исходная ошибка остаётся причиной CrawlError; crawl_many возвращает
её в Outcome.error и сохраняет существующий Crawl. Прямой run поднимает исходную
ошибку. Статистика сохраняется, включая случаи ошибки до первого запроса.

Первичная ошибка не заменяется ошибкой cleanup: вторичные ошибки логируются и
добавляются заметками к первичной. Если первичной ошибки нет, первый сбой cleanup
завершает обход с ошибкой. Отмена остаётся CancelledError с reason='cancelled';
cleanup не превращает её в обычный Outcome.error. Проверить также повторную отмену
во время асинхронного закрытия: очистка не должна оставаться незавершённой задачей.

При раннем выходе из stream open_crawl дожидается завершения обхода и pipeline.
Для раннего выхода из crawl_many сохраняется правило contextlib.aclosing.

## План перехода: отдельные проверяемые шаги

1. Исправить защищённую область Crawl.run: ошибка или отмена start_requests после
   успешного opened должна вызывать closed. Закрепить тестами до рефакторинга.
2. Добавить Settings и внутренний менеджер pipeline, интеграцию с Crawl, обработку
   фатальной ошибки и закрытие. На этом шаге существующий Dataset ещё работает;
   его запись располагается после pipeline и до stream. Это промежуточная
   совместимость коммитов, а не второй рекомендуемый путь в итоговом API.
3. Удалить src/collector/storage, корневые экспорты Dataset/MemoryDataset/SqliteDataset,
   поле Crawl.dataset и параметр dataset во всех entry points. Удалить связанный
   flush-код. Не игнорировать устаревший dataset= молча: вызов получает TypeError.
4. Заменить storage-интеграционные тесты тестами пользовательских pipeline. Удалить
   только тесты удалённого backend API, сохранив проверки ошибок, отмены, streaming
   и изоляции обходов. Обновить package exports и примеры.
5. Документировать несовместимость и миграцию. Существующие файлы SQLite не изменять
   и не удалять. Исторические specs/plans не переписывать; отметить новый дизайн
   как заменяющий прежний dataset-storage design. Выпуск и обновление потребителей
   выполняются отдельно; не публиковать и не сливать ветку автоматически.

## Критерии приёмки

- Объявленный через Settings компонент работает в одиночном и групповом запуске.
- Один класс в нескольких обходах получает разные экземпляры pipeline.
- Цепочка передаёт преобразованное значение, включая None, в stream и collect.
- Ошибка pipeline фатальна даже при max_errors=None; соседний обход успешен.
- Пустой набор pipeline сохраняет прежнее поведение обработки items.
- Стартовые запросы видят открытый sink; closed краулера видит ещё открытый ресурс.
- Ошибка второго open закрывает первый компонент; ошибка close не мешает остальным.
- Ошибка и отмена start_requests, ошибка consumer, ранний break, обычная и повторная
  отмена не оставляют работников/ресурсы; первичная причина не теряется.
- Общая конфигурация не становится хранилищем состояния компонентов.
- Нет зависимости от MongoDB, предметных классов или импортов consumer.
- В актуальном коде и примерах нет Dataset и dataset=; changelog и migration note
  явно перечисляют удалённый API и ответственность приложения за старые данные.
- Полный обычный offline pytest и ruff проходят. Network/live/DB тесты не запускать.
